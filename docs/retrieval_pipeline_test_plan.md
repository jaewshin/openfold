# Retrieval-Augmented Folding Pipeline Test Plan

This plan validates the retrieval-augmented pipeline built around:

- `openfold/model/retrieval_fusion.py`
- `openfold/model/retrieval_augmented_folding.py`
- data generated by `scripts/retrieval/download_structures.py`

The goal is to verify that data loading, retrieval injection, fusion, OpenFold forwarding, and output bookkeeping work correctly **before** the full retrieval index is ready.

---


## 0) Command quickstart

From the repository root, run:

```bash
DATASET_DIR=/absolute/path/to/rag_data

python scripts/retrieval/testing/validate_retrieval_fixture.py --dataset_dir "$DATASET_DIR"
python scripts/retrieval/testing/test_retrieval_fusion_modules.py
python scripts/retrieval/testing/smoke_test_retrieval_augmented_wrapper.py
```

These scripts are provided under `scripts/retrieval/testing/`.

---

## 1) Scope and assumptions

### In scope

1. Sequence/structure data consistency from downloaded artifacts.
2. Forward-path correctness with manually provided retrieved sequences.
3. Shape and masking correctness through retriever/fusion modules.
4. Basic gradient flow to retriever/fusion while OpenFold remains frozen.
5. Smoke-level structure output generation and metadata emission.

### Out of scope (for now)

1. Retrieval quality / recall metrics (e.g., top-k correctness against a real index).
2. Index build performance and ANN infrastructure.
3. Full training convergence.

### Temporary retrieval assumption

For all integration tests below, retrieval candidates can be manually supplied and may include the exact query sequence itself (identity retrieval) or close variants.

---

## 2) Test data preparation (from `download_structures.py` output)

Use the generated dataset directory containing:

- `metadata.json`
- `splits.json`
- `train.fasta`
- `val.fasta`
- `structures/*.cif.gz`

Create a deterministic mini-fixture (`tests/test_data/retrieval_smoke/`) with:

1. **8 train chains + 2 val chains** from your existing split files.
2. Their corresponding mmCIF files.
3. A small JSON mapping `{sample_id -> sequence, structure_path}`.
4. Optional precomputed embeddings if already available; otherwise generate on the fly.

Selection rules:

- At least one short chain (~80 aa), one medium (~250 aa), one longer (~700 aa).
- Include at least one case with uncommon residues to stress masking/featurization.
- Include one intentionally malformed sample (missing CIF or bad sequence chars) for failure-path checks.

---

## 3) Layered validation strategy

## A. Data integrity checks

Run a lightweight validator script over the mini-fixture:

1. FASTA entry count matches metadata count.
2. Every selected entry has an accessible CIF file.
3. Sequence length is within expected range for your pipeline.
4. No duplicate IDs in the fixture.
5. Train/val labels are consistent with `splits.json`.

**Pass criteria:** zero mismatches; malformed sample is caught with a clear error message.

---

## B. Module-level tests (`retrieval_fusion.py`)

### B1. `EmbeddingRetriever` behavior

Using synthetic embeddings with fixed random seed:

1. Verify output shapes: `scores[K]`, `indices[K]`, `retrieved[K, N_d, D]`.
2. Verify `scores.sum()` is ~1 (softmax over top-k).
3. Verify `K == min(top_k, M)` when database is smaller than `top_k`.
4. Verify masks affect pooling (masked residues excluded from means).

### B2. `CrossAttentionFusion` behavior

1. Verify fused output has same shape as query embedding.
2. Verify no NaN/Inf in fused output for valid masks.
3. Gate sanity:
   - with default gate init near 0, fusion effect should be small.
   - after manually setting gate high, fusion contribution should measurably increase.
4. Mask sanity: masking all key/value positions should be handled explicitly
   (either via guard logic or expected failure with informative message).

**Pass criteria:** all assertions hold, deterministic under fixed seed.

---

## C. Model-wrapper tests (`retrieval_augmented_folding.py`)

### C1. Forward smoke test with manual retrieval

For 1-2 samples from fixture:

1. Build `batch` with required OpenFold SoloSeq features including `seq_embedding`.
2. Manually set `db_embs` to include:
   - exact query embedding,
   - one random unrelated embedding,
   - one length-mismatched but valid embedding (if supported).
3. Run `RetrievalAugmentedFolding.forward`.

Assertions:

1. Output contains normal OpenFold keys plus:
   - `retrieval_scores`
   - `retrieval_indices`
2. `batch["seq_embedding"]` gets replaced across all recycle copies.
3. Retrieval metadata shapes match configured `top_k`.

### C2. Freeze/grad-flow test

1. Compute a small scalar loss from model outputs (or surrogate).
2. Backprop once.
3. Assert:
   - retriever/fusion params have gradients,
   - OpenFold params remain `requires_grad=False` and have no gradients.

**Pass criteria:** forward succeeds and gradient ownership is exactly as intended.

---

## D. End-to-end script-level smoke test (pipeline harness)

Create a small harness script (or pytest integration test) that executes one end-to-end pass:

1. Load one query from `val.fasta` and its structure.
2. Construct retrieval set manually (query-identical + 2 others).
3. Build features -> run retrieval-augmented model -> write outputs to temp dir.
4. Record minimal metrics/logs:
   - runtime,
   - output tensor shapes,
   - presence of coordinates/pLDDT-like confidence outputs,
   - retrieval scores/indices.

**Pass criteria:** script exits 0, writes expected outputs, no NaN/Inf in key tensors.

---

## E. Negative and robustness tests

1. **Missing retrieval entries:** empty `db_embs` should fail fast with clear message.
2. **Dimension mismatch:** embedding dim not equal to model expectation should raise explicit error.
3. **Mask mismatch:** bad `db_masks` shape should raise explicit error.
4. **Overlong sequence:** if beyond configured limits, reject early with actionable guidance.
5. **Corrupt structure file:** parser error should identify file and sample ID.

**Pass criteria:** failures are deterministic and user-actionable.

---

## 4) Suggested execution matrix

Run the following matrix before index integration:

1. CPU-only smoke on fixture (quick correctness).
2. Single-GPU smoke on fixture (device compatibility).
3. Two random seeds for module-level tests (stability).
4. Two `top_k` settings (e.g., 1 and 4) to stress score normalization and indexing.

---

## 5) Exit criteria before enabling real retrieval index

You are ready to plug in real retrieval when all conditions hold:

1. Data integrity checks pass on fixture and at least one larger sample batch.
2. Module-level retriever/fusion tests pass.
3. Model-wrapper forward + grad-flow tests pass.
4. End-to-end harness completes for train and val examples.
5. Negative tests produce clear, expected failures.

---

## 6) Practical notes for manual retrieval phase

1. Start with `top_k=1` and query-identical retrieval to isolate plumbing.
2. Then move to `top_k>1` with mixed similar/dissimilar sequences.
3. Log retrieved IDs/sequences alongside `retrieval_scores` to verify bookkeeping.
4. Keep a fixed small fixture under version control for repeatable CI checks.

This staged process lets you validate pipeline correctness independently from retrieval-index readiness, reducing debugging scope when you later switch to live ANN retrieval.
